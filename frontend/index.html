What will happen?

The app calculates the same answer twice: first with one CPU thread, then with several OpenMP threads. It checks that both answers match and measures the time. Parallel processing is not guaranteed to be faster for every dataset.

REPORT
The report in four lines




01
Problem
“Is parallel processing really faster?” depends on the data size, the operation and the machine. Claims need measurements, not assumptions.


02
Approach
Compile one Cython kernel in a sequential and an OpenMP form, run both on the same prepared data and compare them fairly.


03
Measured
Median compute time, speed-up, efficiency and time saved — plus live CPU, RAM, disk, GPU and process telemetry from the operating system.


04
Takeaway
Parallel wins when each thread gets enough work to outweigh the cost of coordinating threads. Near 1× is a valid, explained result.

METRICS
How the numbers are defined




SPEED-UPmedian(Tseq) ÷ median(Tpar)
Above 1× means parallel finished sooner. Below 1× means one thread was faster.


EFFICIENCYnative speed-up ÷ observed threads × 100
100 % would be perfect scaling. Real programs lose some to coordination and memory limits.


TIME SAVED(Tseq − Tpar) ÷ Tseq × 100
The share of the single-thread time that parallel removed (negative if it was slower).




Why can parallel be only ~1× on a small or memory-bound job?
Starting threads, splitting blocks and merging partial results cost time. When the data fits few blocks, or the loop is limited by memory bandwidth rather than arithmetic, extra threads have little to speed up. The app measures this instead of hiding it, and it only recommends a setting it has actually tested on the same dataset.
